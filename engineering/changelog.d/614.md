- engineering-loop: the gatekeeper is `scripts/gatekeeper.py`, with its contract CLI: `check build|queue|merge`, `record approval|verdict|checks`, `land [--wait]`, `report [--json]`, plus `batch` and `delegate`, exit codes 0, 1 and 3 as before. `record checks [pr]` runs the policy's `checks.check` (else `mise run check`) on the head and records the pass as `local-ci` does; `--all` runs `checks.all` and is `local-ci`. `report --json` prints a verifier report's facts (head, counts, satisfied, risk, findings, question) as one JSON object, refusing what `report` refuses. Its GitHub calls move behind three ports, tracker, forge and evidence, in `scripts/github_adapter.py`; the evidence port both writes and reads the approval records, verdicts and check passes the gate checks; the tracker port also reads an issue's children (its sub-issues); the policy's new `adapters` section names each port's adapter, `github` by default, and an unknown name is refused naming it. The gate accepts its own status under either name, `loop:approvals` or `gatekeeper`: `check merge` waits for neither and `land` reruns either; the project template's workflow posts `loop:approvals`. `scripts/approvals.py` and its verbs (`approve`, `verdict`, `local-ci`) keep working for one release line, running `gatekeeper.py` (#614).
